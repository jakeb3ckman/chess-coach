## 3. The 12× slowdown: cause, fix, and whether it can happen on GitHub

There were two separate problems in the first Mac run.

**Problem A: the job never finished. It was a real bug, now fixed.**

- **Cause:** python-chess starts a background thread for each engine (`chess/engine.py`, line 76). That thread is not a "daemon" thread, so Python waits for it before a worker process can exit.
  - The first runner used Python's `ProcessPoolExecutor`, which waits for every worker to exit when it shuts down. So it waited forever.
- **Confirmed:** the old code, run again on a quiet Mac, still hung at shutdown with 10 Stockfish processes left running.
- **Fix:** `coach/runner.py` now runs its own worker processes.
  - Each worker quits its engine when it is told to stop.
  - The main process notices a worker that dies, and terminates any worker left over at the end.
- **Since the fix:** there have been no hangs. That covers the Mac runs, the 6 GitHub analysis jobs and the verify job.
- **Could it happen on GitHub?** Yes, this one would have. A hung job would have sat until the 340-minute job timeout, wasting the run, although committed batches would have been kept. The fix applies everywhere.

**Problem B: games took 12× longer. Cause: the Mac was overloaded by other programs. Not a code problem.**

- **What happened:** the first 20 games averaged 270 s of engine time each, against about 33 s normally. The slowest took 530 s.
  - The Mac's load average was 37–39 on 12 cores, while the 10 engines account for only about 10 of that.
  - Just after the run, Spotlight indexing (`corespotlightd`) was using 188% CPU and the Claude app's renderer 265%.
- **Experiments on a quiet Mac:**
  - The old code ran 20 games in 70.6 s, which is normal speed. So the code was not what made it slow.
  - Writing 3,227 new files right before a test, to try to trigger Spotlight, ran at normal speed (75.9 s).
  - A freshly copied Stockfish binary with 10 engines at once ran at 657k nodes/s, against 741k before. That is not a 12× effect.
- **Conclusion:**
  - The slowdown came from other programs competing for the CPU at that moment.
  - I could not identify the exact program, because the macOS system log is not readable from this environment. Treat the cause as likely, not proven.
  - Because the search uses a fixed node count, a slow machine changes only how long the analysis takes, never its results. The 30/30 repeatability check confirms this.
- **Could it happen on GitHub?** Very unlikely at this size.
  - Each GitHub job runs on a fresh, dedicated virtual machine with no desktop apps or indexing.
  - Over the 2,462-game backfill, per-game times stayed steady within each shard (median 46–69 s, 99th percentile 126–174 s, worst 232 s). Nothing like 270–530 s.
- **What did vary on GitHub:** two shards ran about 1.5× slower per game than the other two (means 74 and 70 s against 50 and 49 s).
  - The likely cause is that GitHub put them on different CPU models. The analysis job does not log the CPU model, so this is not confirmed.
  - It does not affect results.
- **If a runner were ever slow:**
  - the 300-minute budget stops new work in time
  - finished batches are already committed
  - the next run picks up the rest
  - every analysis file records its engine time (`secs`), so a slowdown would be visible in the data

## 7. How to read the numbers below

- **Win%:** the chance of winning from the side to move. It is computed from Stockfish's evaluation with the Lichess formula (spec section 4).
  - "Drop" is how many Win% points my move lost compared with the engine's best move.
  - inaccuracy = drop of 5 or more; mistake = 10 or more; blunder = 15 or more.
- **Eval convention:** evals in the samples are shown **from my side**, so + means I am better.
  - "Mate in 1 for me" counts as 97.5 Win%, the Lichess convention (mate is treated as ±1000 cp).
- **Cards:** only mistakes and blunders can become cards. A card also needs all of the following:
  - The best move is clearly better than the second-best (gap of at least 15 Win%, checked with MultiPV 2).
  - I was not already lost: at least 10 Win% before the move.
  - I was not already winning comfortably: above 90 Win% before and still 50 or more after. A thrown-away win, from above 90 to below 50, is kept.
  - I was not in severe time trouble: the clock before the move was at least min(15 s, 10% of the base time).
  - The position is not already in the deck. Positions are de-duplicated by board, side to move, castling and en passant.
- **What the zeros in the funnel mean:** two rows show 0. Both follow from the definitions, not from a bug.
  - "Already lost": a drop of 10 or more needs at least 10 Win% to start with. So no mistake can start below 10, and the rule only matters for inaccuracies, which never become cards. It stays as a safeguard if thresholds change.
  - "No deep check": every move that pass 1 marks with a drop of 7 or more gets a deep check. A mistake needs a drop of 10, so every mistake has had one.
- **Ordering:** cards are introduced in the approved order, 10 per day:
  1. most occurrences
  2. most recent
  3. biggest drop

- **Games that can't be played back normally:** variants and custom starting positions are rejected by the importer.
  - None turned up in the real data, but tests cover them.

**Uncertain or not fully verified:**
1. **New games on GitHub:** a new game arriving on GitHub has not happened yet (section 1). The first nightly run after I play will be the first real test.
2. **Clock increments:** time spent per move is computed as clock before − clock after + increment.
   - This assumes both sites record the clock after the increment is added. I have not checked this against a site's own move-time display.
   - It affects only the "time spent" column. Time-trouble filtering uses the clock before the move, which does not depend on this.
3. **Pass-1 screen can miss mistakes:** a move is deep-checked only if the quick pass shows a drop of 7 or more.
   - If the deep search would have rated a move a mistake but the quick pass saw less than 7, it is missed. I don't know how often this happens.
   - Measuring it would mean deep-checking every move, about 10× the engine time.
4. **Chess.com delay:** Chess.com's monthly archives can show a new game up to about a day late. Such games are picked up the next night.
   - **Lichess:** the importer asks for games created since one day before the newest stored game and removes duplicates. That covers any game long enough to span midnight.
5. **Chess.com links don't open at the move:** Chess.com game links open at the start of the game, not at the move.
   - Every sample therefore also has a Lichess analysis-board link that opens the exact position. Lichess links open at the move.
6. **GitHub hardware varies:** two analysis shards ran about 1.5× slower than the other two, probably on different hardware.
   - The analysis job doesn't log the CPU model. Results are unaffected (section 4).
7. **Timing exclusions:** the 20 games from the slowed-down first Mac run are excluded from speed figures.
   - Their analysis results are kept, because results don't depend on speed.
8. **Misleading commit message:** the GitHub import step commits with the message "import: new games" even when only the importer's bookkeeping changed (for example, the time the current month was last fetched).
   - Commit 6d01b75 is such a commit: no games, one line of state. This is cosmetic.
9. **No license file:** the repository has no LICENSE file.
   - python-chess is licensed under GPL-3.0, so any license added later must be GPL-compatible.
   - This needs a decision from you. Until then, others may read the public code but have no right to reuse it.
10. **Stuck terminal tab:** the Claude app's Terminal panel has a stuck tab ("c1") left over from the GitHub sign-in. It is harmless, and you can close it.
